CASCADE RESPONSE — DIRECT API vs MCP, AND YES IT IS THE SAME CONCEPT
================================================================================

DIRECT ANSWER: YES, exactly what we are building. AND it is cheaper + simpler.

WHAT MCP IS (conceptually)
  MCP = Model Context Protocol
  It is a standard way for LLM to call tools (functions) via a structured protocol:
    LLM -> MCP server -> tool execution -> result back to LLM
  Cost: extra API round-trips for tool discovery, schema fetching, response parsing
  Overhead: server processes, network hops, JSON schemas per tool

WHAT WE ARE DOING (same idea, without MCP overhead)
  Our agents = same concept as MCP tools, but:
    No protocol overhead — direct function calls in Python
    No tool schema discovery — we write the prompt with the schema embedded
    No extra API calls — one Groq call -> parse JSON -> call bpy/ffmpeg directly
  
  Example:
    MCP approach:  LLM -> MCP handshake -> tool list -> call set_camera -> response
    Our approach:  Groq(simple_prompt) -> JSON parse -> bpy.data.objects['Camera']...

  Cost difference:
    MCP with GPT-4:   ~$0.01-0.05 per scene (tool calls + context)
    Our Groq approach: ~$0.0001-0.001 per scene (Groq is 10-100x cheaper)

WHY SIMPLE PROMPTS WORK BETTER HERE
  Our domain is closed (fixed menus: states, gestures, emotions, shot types)
  Small fast models (llama-3.1-8b on Groq) handle closed menus perfectly
  One prompt per beat, no chain-of-thought needed
  Already proven: body_director_agent.py does this today and works well

SO THE ARCHITECTURE IS
  Text input
    -> Groq (llama-3.1-8b, $0.0001/call) -> beat list JSON        [ScriptAgent]
    -> per beat: rule-based camera/lighting decisions              [CameraAgent]
    -> existing FaceCoordinator + BodyDirectorAgent                [already done]
    -> Blender HTTP server (bpy) renders the frame                 [RenderAgent]
    -> ffmpeg stitches clips + audio -> MP4                        [RenderAgent]
  
  Total cost per 2-min clip: ~$0.001-0.005 (Groq free tier: 6000 req/min)
  Groq free tier is MORE THAN ENOUGH for this pipeline.

ANSWER TO "DO WE INDIRECTLY DO THE SAME AS MCP TO POWERFUL AI APIS"
  YES — conceptually identical. We are building a lightweight custom MCP:
    Our blender_director_server.py = MCP server
    Our agent JSON calls = MCP tool calls  
    Our llm_fw = MCP client
  But without the protocol overhead, without the cost, without the dependencies.
  This is the RIGHT approach for a self-contained movie pipeline.

CASCADE RESPONSE — FAST + CINEMATIC CAMERA MOTION
================================================================================

YES — camera MOTION (not just position) is what makes it cinematic.
Static camera = TV news. Moving camera = movie.

CINEMATIC CAMERA MOVES (what we need to generate)
  dolly in   = camera moves toward subject (intensity, intimacy)
  dolly out  = pulls back (reveal, isolation)
  pan        = rotates left/right (follows movement, reveals space)
  tilt       = rotates up/down (power, emotion)
  crane up   = rises (epic, god-view)
  truck      = moves sideways (tracking walking character)
  push+zoom  = Vertigo effect (focus on face, background distorts)

HOW TO GENERATE IN BLENDER (keyframes, not just set_location)
  Not: camera.location = [x,y,z]  <- static, not cinematic
  Yes: 
    frame 0:  camera.location = start_pos, insert_keyframe
    frame 30: camera.location = end_pos,   insert_keyframe
    set interpolation = BEZIER (smooth ease in/out)
  Blender animates the path between keyframes automatically.

HOW TO MAKE THE WHOLE PROCESS FAST + AGENTIC
---------------------------------------------
KEY INSIGHT: Process the WHOLE script in ONE Groq call, not per beat.

  SLOW (per beat):  beat1 -> Groq -> beat2 -> Groq -> beat3 -> ...  (N API calls)
  FAST (whole):     all beats -> ONE Groq call -> all camera moves at once

  One Groq call (llama-3.1-8b) processes 2-min script = ~0.5 seconds total
  Then ALL camera keyframes are known before any rendering starts.

FAST PIPELINE (whole script at once)
  STEP 1 (~0.5s): ScriptAgent: full text -> ONE Groq call -> all beats JSON
  STEP 2 (~0.1s): CameraAgent: all beats -> camera keyframe curves (rule-based, no LLM)
  STEP 3 (~0.5s): VoiceAgent: full text -> Parler TTS -> WAV  [parallel to step 2]
  STEP 4 (~0.5s): LipSync: WAV -> wav2arkit -> blendshapes per frame
  STEP 5 (~1-2s): Load all into Blender: camera curves + face + body + lighting
  STEP 6 (FAST):  EEVEE render: 30-60 FPS on GPU = 2min clip in ~4-8 seconds!
  STEP 7 (~1s):   ffmpeg: composite frames + WAV -> MP4

  TOTAL TIME FOR 2-MIN MOVIE CLIP: ~10-15 seconds end to end (with GPU)
  Without GPU (CPU EEVEE): ~2-5 minutes (still usable)

CAMERA MOTION GENERATION (rule-based = no LLM needed = fast)
  Based on beat dict:
    action = walk          -> truck camera (move sideways at walk speed)
    emotion = angry, int>0.7 -> slow dolly in (0.3m over 48 frames)

    gesture_target=camera -> lock camera, subtle push in
    state=stand           -> static or very slow push (~0.05m over beat)

  These are lookup tables + simple math. Zero LLM calls for camera.
  One Python dict maps (emotion, state, gesture) -> (move_type, speed, distance)

REASON 1: WORLD-SPACE BUG (fixable by root-local retraining)
  DecompressorNet is trained on absolute world positions.
  The feature vector has NO absolute position info.
  So decomp outputs the MEAN pose of the dataset.
  The dataset mean ≈ walking pose (most common action in HumanML3D).
  Result: walk/run look like their mean → gait visible.
           jump/kick/wave look like walking too (wrong).
  
  Fix: root-local retraining. After fix, decomp will learn actual pose articulation
  → jump = crouching then extending, kick = one leg swings high, wave = arm raises.

REASON 2: DATASET IMBALANCE (partially fixable, inherent limitation)
  HumanML3D clip distribution (approximate):
    Walking/running:   ~45% of all clips
    Sports/dynamic:   ~25% (jump, kick, dance)
    Arm gestures:     ~15% (wave, raise arms, clap)
    Static/sitting:   ~15%
  
  StepperNet sees walking 45% of training steps → becomes a walking expert.
  Jump/kick/wave are seen rarely → model doesn't learn them as well.
  Result: when you prompt "wave hand", StepperNet still generates walking-like features.
  
  Fix: more training (300→500 epochs on Stage 2), or data augmentation (not easy here).

REASON 3: TRANSIENT vs PERIODIC MOTION (architecture limitation, not fixable easily)
  Walking: PERIODIC motion. Same gait cycle repeats. Easy to learn.
  Jumping: TRANSIENT motion. Happens once: squat → jump → peak → land. 3 different phases.
  Kicking: TRANSIENT. Wind-up → kick → follow-through. 3 phases in ~0.5 sec.
  Waving:  PERIODIC but small amplitude arm circles. Easy to lose in MSE averaging.
  
  MSE loss teaches the network to predict the AVERAGE across all frames.
  For transient actions, the "average" is somewhere between phases → looks like drift.
  For periodic actions, the "average" has structure → looks like gait.
  
  Fix: this requires a better loss (perceptual/discriminator) or larger model. Hard.
